# B10–B12 配对仿真协议

状态：运行前固定参数的探索性实验协议；不是正式预注册，不是结果报告，也不是论文
首创性证明。下述方法细节按本轮实际实现记录，不把先前概念方案视作已完整实现。
三种改进以嵌套增量实现，不把组合方案描述成互斥的独立算法。所有性能下降、运行失败
和无收益结果均保留。没有离线 GP 训练，也不实施 RDMA 路径恢复或已发送 chunk 迁移。

## 问题与对照

| 标签 | 定义 | 主要增量对照 |
|---|---|---|
| B8 | 最近完成 chunk 的端侧速率反馈 | 现有实用基线 |
| B9 | ACK 到达时用未完成 chunk 的等待时间上界压低速率 | 既有等待修正基线 |
| B10 | 负载条件下的等待异常模型；ACK 与 10 μs 定时检查 | 相比 B8/B9，健康波动损失与故障后的额度调整 |
| B11 | B10 加端侧未完成工作量的预计完成时间调度 | B11 对 B10，隔离调度目标增量 |
| B12 | B11 加拓扑映射、有限状态的交换机出口证据 | B12 对 B11，隔离在线交换机信息增量 |
| B12_no_signal | 运行 B12 代码，但禁用信号采集与送达 | 检查退化为 B11 的一致性 |
| B12_shadow | 采集与送达同 B12，但不让信号影响调度 | 检查纯信号事件对仿真的影响 |
| B12_ideal | 同一 10 μs 采样，送达延迟改为 0 | 仅为送达延迟消融，不是全知容量 Oracle |

只有前五组进入默认主矩阵。后三组必须显式选择，不能在看到结果后用最优变体替换 B12
而仍声称它是原始主比较。运行时的封存动态库决定实际实现；算法参数变更必须新建输出根。

## 本轮具体方法与未实现项

### B10：条件对数时延启发式，不是生存概率

实现位置：`astra-sim/network_frontend/ns3/limer_wait_model.h`、`limer_split_runtime.h`。
模型条件为源 GPU、rail、chunk 字节数的 ceil(log2) 桶，以及该 chunk 分配时本源在
该 rail 的在途 chunk 数 ceil(log2) 桶（包括自己）。这个负载条件在分配时固定，完成
统计和未完成查询均使用同一条件；本轮没有按目的 GPU/具体路径类别分别建模。

每个条件收集从真实 first-TX 到完成 ACK 的 `log(duration_ns)`。前 8 次完成构成
冷启动均值/方差，此前不施加等待惩罚。成熟后采用 alpha=1/32 的鲁棒 EWMA：残差
裁剪到 ±2 sigma；高于均值加 3 sigma 的正向异常不纳入正常历史。sigma 至少为
`ln(1.25)`，故等待阈值至少为几何均值的 `1.25^3 ≈ 1.953` 倍。条件总数上限 4096；
达到上限时新条件保持冷启动，不淘汰已有参考，也不借用其他源/rail 的统计。

对未完成 chunk 的 age，使用 `factor=max(0.1,min(1,threshold_ns/age_ns))`。每源/rail
取有效在途 chunk 中最小的 factor，在 ACK 和每 10 μs 的本地检查事件更新。B10 将
最近完成速率乘以该因子，随后使用 B8 式字节额度分配。

这只是有负载条件的对数时延阈值模型，**不是校准后的生存分布、phi 分数或故障概率**。
冷启动期间故障会污染参考；正常永久负载变化也可能被当成正向异常；同一 rail 的
最小因子仍可能过于保守。没有外部故障标签、GP 或离线训练。

### B11：本源未完成字节的完成代价代理

实现位置：`astra-sim/network_frontend/ns3/limer_split_policy.h` 的 `Select`。
保留双 rail 各一次初始探测后，为下一个大小 x 的 chunk 比较
`cost_r = 8 × (reserved_local_r + x) / adjusted_rate_r`，选择代价较小的 rail；相同
代价选 A。`adjusted_rate` 来自 B10 的最近完成速率与等待因子。

`reserved_local` 只是当前源 GPU 在这个 rail 已分配而尚未完成的唯一 payload 总量，
不是交换机队列、接收端全局预留或整个系统的在途流量。多个并发 QP 并非被精确建模为
一台串行服务器，因此这是调度代价代理，不是精确预测完成时间。

本轮保持固定 64 KiB chunk，没有实现先前概念方案中的可变 chunk 尾部模式、按
collective 关键路径排序或在途 chunk 搬迁；不得将这些能力归入 B11 的结果。

### B12：有需求迹象的交换机出口速率下降证据

实现位置：`astra-sim/network_frontend/ns3/limer_sparse_signal.h` 与 runtime 的
`SwitchTick/ReceiveSignal`。监测每个 GPU 对应的两个交换机 ACCESS 出口，共 32 个
方向端口。传感器每 10 μs 读取已有 TX 字节计数、队列与 link-up 状态。

窗口首尾队列均非空才记为有需求迹象；它不证明整个窗口持续饱和。窗口速率用 TX
字节计数差除以时间；TX 在序列化开始时计数，不能称为目的端有效 goodput。参考为
有需求窗口中观察到的最大 wire 速率，不读取链路真实故障比例或未来容量。

连续两个有需求窗口低于参考的 0.7 倍才降低 factor，以当前速率/参考比例作为因子，
范围为 [0.1,1]；无需求迹象或未达到连续低速条件时恢复为 1。link down 因子为 0.1，
但本矩阵注入的是 carrier-up 降速，不据此声称硬断链检测通过。

首次采样、factor 相比最后发送值变化至少 0.1、或距离上次报告达到 40 μs 时发送报告。
只向其他服务器的 12 个源主机订阅者建模送达，默认延迟 10 μs；主机只使用已经送达且
从采样时刻起不超过 50 μs 的因子。以 `min(wait_factor,signal_factor)` 修正最近完成
速率，不把两个相关证据的因子相乘；随后执行 B11 的完成代价选择。

端口算法状态静态断言不超过 48 B，这个预算**不包括已有硬件计数器、拓扑和订阅者
元数据、采样定时器、主机缓存、事件队列、导出日志**。没有实现 P4/ASIC 部署，不能从
C++ 结构体大小推导真实芯片资源占用。每报告 32 B 也是逻辑消息 payload 假设。

## 固定实验配置

| 参数 | 固定值 |
|---|---|
| 拓扑 | true-16，4 服务器，每台 4 GPU，两独立 fabric 平面、每 GPU 两个 ACCESS |
| 验证 | `validate_true16_dualrail.py` 验证物理拓扑；每次检查 16 rank 全完成 |
| 工作负载 | `microAllReduce_16rank_split_64mib.txt`，每 GPU 输入 64 MiB |
| chunk / 并发 | 64 KiB，每源 GPU 最多 8 个在途 chunk |
| 预期跨服务器有效 payload | 503316480 字节；检查 chunk 区间无重复、缺失、pending |
| 随机故障 | 冻结种子 42/43/44；32 条 ACCESS 中已选的 8 条，减速上限 80% |
| 故障机制 | `service_degradation`；carrier 保持 up，按冻结比例降低服务速率 |
| 周期诊断遥测 | 1 ms；不等于 B12 的独立传感器采样周期 |
| B10–B12 等待检查 | 10 μs；B8/B9 不增加该检查定时器 |
| B12 采样 / 送达 / TTL | 10 / 10 / 50 μs |
| B12 心跳 | 40 μs，变化事件也可发送；每条报告的具体条件以实现为准 |
| B12 交换机状态预算 | 每监测端口 48 B；拓扑映射、计时器和主机缓存单独计，不声称全系统仅 48 B |
| B12 报告预算 | 每报告 32 B 逻辑 payload，向其他服务器 12 个主机订阅者送达 |
| 执行 | 单个模拟器 worker、逐次顺序运行，每次 wall-clock timeout 180 s |
| 观察上限 | 100 ms 仿真时间；工作负载完成后允许提前结束 |

B12 本轮只监测可验证需求的 **交换机到主机 ACCESS 出口**。不把这类信号外推为
全方向或全路径瞬时容量观测。故障注入器可以读取故障时间表；调度器不得读取故障
状态、真实服务比例、未来时间表、容量 Oracle 或其他主机的全局预留。

控制消息具有明确采样时刻、逻辑送达时刻与 TTL，但本轮不消耗真实数据平面带宽，也未
加入报文头或控制消息排队丢失。汇总报告同时记录原始报告数、计划 fanout payload 和
实际已送达 payload；不得将它们写成已测得的线上 wire 开销。

## 验收、分析与解释边界

主终点是仿真零点到全部 16 rank 的 `WORKLOAD_COMPLETE` 时间，单位 ns，展示时可换算
为 ms。`transport_span_ns` 为辅助指标，不与主终点混用。配对变化计算为
`100 × (T_policy / T_reference − 1)`，负数表示更快；保存对 B8/B9/B10/B11 的原始配对值。

每次运行均需通过：正常进程退出、chunk 和 ACK 一一对应、全部有效 payload 一致、
16 rank 完成、反馈证据审计，以及故障实际应用的精确链路、参数与纳秒时间核验。
对 workload 完成之前应发生的 revert 也进行核验；完成之后的未来事件不要求执行。
健康场景不得出现任何故障应用事件。

还记录故障前已分配比例、故障后流向受影响路径的字节数、最后完成 chunk、B12 逻辑
控制开销。受影响路径上的字节不一律称为误分配；慢路径仍可能提供有用服务。

按场景族分别比较，不把健康、早期故障和恢复混成一个能掩盖退化的平均值。只有三个
既有故障种子，分析是描述性和探索性的；不宣称显著性、总体可靠性或对真实 NCCL 的
性能保证。若之后调参，必须注明并使用新种子独立验证，不回写本协议下的原始结果。

本轮不验证 tensor 数值、不运行真实 NCCL，不证明 hard disconnect 恢复、不证明
检测时间达标。调度计算本身的 CPU 成本未加到仿真时间；任何未建模成本必须单独列明。
首次风险下降/首次信号均不自动等于真实故障检测时刻。

## 复现与断点续跑

从 `SimAI/` 运行；编译由主实验协调者先完成，runner 不在运行过程中重编译。

```bash
python3 limer/tools/run_adaptive_comparison.py \
  --binary ns-3-alibabacloud/simulation/build/scratch/ns3.36.1-AstraSimNetwork-debug \
  --topology limer/results/true16_hard_fault_e2e/topology/Spectrum-X_16g_4gps_DualToR_DualPlane_100Gbps_A100 \
  --frozen limer/results/split_baselines/random_a8_b80_t1ms_20260908 \
  --out limer/results/split_baselines/NEW_ADAPTIVE_COMPARISON
```

首轮 smoke 可增加 `--scenarios healthy standard_42 --policies B8 B10 B11 B12`。
之后使用同一输出根、不加筛选即可扩展到完整 50 次；完成的运行重新核验后复用。
可选消融为 `--scenarios healthy standard --policies B12_no_signal B12_shadow B12_ideal`。
本轮随后扩展正常送达 shadow 到其余六个场景，参数为
`--scenarios early recovery --policies B12_shadow`。这六次是结果检查阶段增加的消融，
不是五政策主矩阵的一部分。发现零延迟无干预也改变结果后，又在独立新根执行四次
`run_zero_delay_shadow.py` 对照；详见结果报告，不更改这里的主矩阵及原始参数。

首次运行先写 `protocol.json`，记录封存运行时闭包、输入 SHA256、冻结故障哈希和参数。
每个场景生成固定 fault CSV，每个 run 保存 manifest、原始证据、`result.json` 及证据哈希。
`summary.json` 与 `paired.csv` 每完成一轮更新。子集命令退出成功只代表所选运行通过；
全主矩阵的完成状态单独保存在 `main_matrix_complete` 与 `pass`，不混淆二者。

续跑不覆盖完成或失败运行；校验已有证据哈希、配置 identity，并重新审计原始 CSV。
缺少退出记录的中断目录保留并停止，需使用新输出根，不能悄悄删除或自动重跑替换。
失败运行也保留在 summary 中。所有处理局限本地，不自动上传代码、日志或结果到 GitHub。

### 仅评估代码修订：显式保留旧结论

如果确认失败来自日志评估器而非模拟器，可以使用额外参数
`--reaudit-existing --reaudit-reason '具体评估错误及修复原因'`，并通过场景/政策筛选指定
已有运行。这一模式**完全不执行模拟器**，要求每个选中目录已有 result、模拟器退出码
为零，且当前原始 CSV、manifest、退出记录的 SHA256 与旧 result 一致。故障时间表、
protocol 和封存运行时 identity 也必须一致。缺少 result 或原始证据改变均拒绝修订。

如果重新评估的派生结果变化，先在该运行的 `audit_revisions/0001/`（后续顺延）保存
旧 result 的原始字节、新 result、旧 summary 快照、old/new hash、新评估脚本 hash、
UTC 时间与原因，然后原子更新活动 result，再更新 summary/paired.csv。旧评估器 hash
若未记录则明确标为未记录，不推测补填。没有改变的结果不生成空修订。

这仅允许可追溯的评估纠错，不允许更换算法、参数、输入、原始日志或重新执行模拟器
来替换失败。普通 resume 保持原有严格行为，遇到新旧评估差异仍然停止，不自动接受。
